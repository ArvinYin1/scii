# scii

把画面切成格子，用「一个字符有多黑」去代表「这一格有多亮」。

这个仓库起源于一次逆向：看到一个页面里鱼群由字母组成、在水面上游动，于是把它拆开量了一遍，
再顺着同一套渲染思路做了自己的作品。仓库里有四个东西——一个作品、一份讲解、一版复刻、一篇分析。

全部是**单文件 HTML，零依赖、零素材、零构建**，双击就能打开。

## 三个核心技法

逆向和实现过程中真正学到的，其实只有三件事。

### 1 · 网格和字格必须是同一套

一个字符占一格，格子大小由等宽字体的字宽反推——不是拍一个数字。
字宽高比大约 `0.6 : 1`，按正方形算会把画面横向压扁。这是最常见的第一个坑。

### 2 · 一个「颜色」可以当两个标量用

要在离屏画布上叠加很多半透明形状（`globalCompositeOperation = 'lighter'`）时，颜色会被加法搅成一团。
但如果把**总强度 `k`** 和**色相比 `m`** 分别写进 R 和 B 两个通道：

```js
function col(m, k, w) {
  return `rgb(${(1 - m) * k * 255 | 0}, ${w * 255 | 0}, ${m * k * 255 | 0})`;
}
```

叠加之后仍然能反解——因为加法是分开作用在 R 和 B 上的：

```
R + B = k          → 亮度
B / (R + B) = m    → 色相
```

换句话说：**离屏画布不是图片，是数据容器**，三个通道各存一个标量。

### 3 · 字符的「墨水浓度」并不均匀

亮度连续、字符离散，所以需要一张斜坡表。但候选字符的墨水覆盖率分布极不均匀——
`@ # 8 S X` 挤在很窄的高位，`. , ' ;` 全趴在接近 0 的地方。老老实实按顺序当阶梯用，中灰区就会出现明显断层。

低成本的解法是**每档准备两个字，用哈希按格子二选一**，等于给亮度加了抖动，台阶就消失了。

## 性能：不在算法，在「少做」

| 手法 | 省掉的 |
|---|---|
| 锁 30fps | 一半的帧根本不渲染 |
| 只画亮格 | `L < 0.06` 直接跳过，大面积暗部零成本 |
| 量化 + 缓存样式串 | `(色相, 亮度, 白度)` 压成几百个 key，`rgba()` 只拼一次 |
| 小离屏画布 | 降采样交给浏览器，不自己遍历像素 |
| 字形图集 | 列数 200+ 或要 60fps 时才必要，`drawImage` 替代 `fillText` |

列数也不是越多越好：翻倍列数等于四倍字符数，但细节增益远小于成本，字符还会小到认不出来。
好看的实现多数落在 **90–140 列**之间。

## 技术栈

原生 HTML / CSS / JavaScript。没有框架、没有构建步骤、没有第三方库、没有网络请求。

浏览器要求：任何支持 `<canvas>` 与 `requestAnimationFrame` 的现代浏览器。
所有页面都处理了 `devicePixelRatio`、`prefers-reduced-motion`，并在标签页隐藏时暂停动画。
