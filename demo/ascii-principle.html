ASCII rendering · 原理拆解

一张画面，
是怎样变成一片字符的

从视频到字符画，中间没有魔法。它只做了一件事：把画面切成格子，用「一个字符有多黑」去代表「这一格有多亮」。 下面每一步都能现场调参数，你可以亲眼看到每个决定带来的后果。

本质上这是降维：连续的灰度场 → 离散的字符密度等级。
好看的原因不是字符，而是你选择了哪套字符、怎么分级、怎么上色。

01 / 切成网格

一个格子，只装一个字符

把画面横向切成 cols 份、纵向切成 rows 份，每一份就是一个格子。 一个格子最终只会输出一个字符——所以格子的数量，直接等于字符的数量，也直接等于画面能保留多少细节。

先看这条管线。左边是源画面（这里是程序画出来的，方便全程离线），中间是降采样后的采样结果，右边是字符化之后的样子。

第一个坑：字符不是正方形。 等宽字体的一个字，宽高比大约是 0.6 : 1。如果你的格子按正方形算，画面会被横向压扁。 正确做法是先量出字宽，再反推列数——上面这个演示就是按真实字宽算的，所以你拉列数时画面比例不会变。
02 / 每格取什么颜色

「取一个点」和「取一片面积」是两回事

格子落在画面上是一块面积，但你需要的是一个数字。最直觉的做法是取中心那一个像素——这是错的。

画面上到处都是细密的纹理（发丝、布料、噪点、边缘）。单点采样等于对这些纹理做随机抽样， 结果就是：画面自己不动，字符却在疯狂闪。这个现象叫走样（aliasing）。

下面的对比是同一帧、同一网格。关掉平滑时走的是最近邻采样，等于只取一个点；打开时浏览器会做面积平均。 盯住中间那块细纹理区域看。

面积平均的实现不用自己写循环。把画面 drawImage 到一个只有 cols×rows 大的离屏画布上，浏览器就会自动做箱式滤波—— 这一步是免费的面积平均，也是整个方案能跑起来的性能基础。 只需要一个开关：ctx.imageSmoothingEnabled = true。
03 / 在哪里取平均

混合光是线性的，混合像素值不是

「亮度要用 gamma 校正」是这类文章里最常被重复的一句话，但它对纯映射其实没用： 反 gamma 解码算亮度、再编码回显示，两次变换正好互相抵消，结果和直接取 sRGB 几乎一样。

真正会在这一步出问题的是平均。一个格子里往往一半亮一半暗， 你要把它压成一个数。而 127.5 这种"算术平均"在 sRGB 空间做， 和在线性空间做，结果差很多：

在 sRGB 空间平均
→
#7F7F7F · 127
在线性空间平均
→
#BCBCBC · 188

同样的「一半黑一半白」，两种空间给出的数差了 61 级

一半黑一半白，观感上应该偏亮（188），而不是中灰（127）。 所以在 sRGB 空间做平均，会把所有细小的亮部压暗——细线、高光、发丝会先消失。 下面的对比就是这个后果：左边是浏览器默认（sRGB 平均），右边是在线性空间里求平均后再编码回去。

sRGB 空间平均 · 亮部被压暗
线性空间平均 · 亮部保留
什么时候真的必须在意 gamma：只要是「把多个光混在一起」的场合——面积平均、加法混合、 模糊、发光叠加。反过来，单纯拿一个像素算亮度再查字符表，做不做 gamma 几乎看不出来。
04 / 字符斜坡与断层

字符的「墨水浓度」并不均匀

亮度是连续的，字符是离散的。所以需要一张表，把 0→1 的亮度切成若干档，每档对应一个字符。 这张表叫字符斜坡（ramp）。

但这里有个隐蔽的问题：字符的墨水覆盖率分布极不均匀。 下面我把候选字符真正渲染出来、量了每个字符的覆盖率。你会看到 @ # 8 S X 挤在很窄的高位， 而 . , ' ; 全都趴在接近 0 的地方。

如果你老老实实按字符顺序当阶梯用，中灰区域就会出现明显的断层——亮度只变了一点，字符却跳了一档。 下面两个条带对比了两种处理：左：一档一个字；右：每档两个字，用哈希伪随机选。

一档一字 → 看得出来台阶
一档两字 + 哈希 → 台阶消失
右边这招很省事：不用重排字符，只要给每档准备两个字，用哈希按格子选。 视觉上相当于给亮度加了抖动（dither），过渡立刻顺了。
05 / 三种上色思路

字符是骨架，颜色决定气质

字符只负责「形状感」，气质几乎全由颜色决定。下面是同一个画面、同一套字符斜坡下的三种做法：

A 单色终端
B 逐字取色
C 色块反白
策略做法气质 / 代价
A 单色所有字符同一颜色最克制、最像终端；信息最少，靠字符密度撑画面
B 逐字取色每个字符用自己的采样色最还原原画面，但容易糊、失去「字符感」
C 色块反白先铺一层淡色块，再用近白色画字符最有块面感，最「设计」；最亮处可反相成亮底暗字
C 的反相是点睛之笔：在最亮的几档把「暗底亮字」翻成「亮底暗字」， 暗色页面里会突然出现几块亮砖，层次一下就出来了。
06 / 把两个值塞进两个通道

一个「颜色」可以当两个标量用

这是整套技法里最漂亮的一招。当你要在离屏画布上叠加很多半透明形状 （globalCompositeOperation = 'lighter'），颜色会被加法搅拌成一团，之后再也分不开。

但如果你需要同时保留两个互相独立的量——比如「总强度 k」和「色相混合比 m」——可以把它们分别编码进 R 和 B：

加法叠加后
字符化结果

公式只有三行，但含义很关键：

R = (1 − m) · k   冷色分量
B = m · k           暖色分量
G = w              白度 / 高光

叠加发生在这个编码之后，所以加法是分开作用在 R 和 B 上的。解的时候：

R + B = k        → 总强度，拿去查字符档位
B / (R + B) = m  → 混合比，拿去查色相
换句话说：这不是一张图片，而是一个数据容器。三个通道各存一个标量。 只要在解码端知道约定，加法混合就破坏不了它。
07 / 为什么能跑到 30 帧

性能不在算法，在「少做」

一屏几百上千个格子，如果每帧每个格子都 fillText 一次，加上拼颜色字符串， 开销会迅速吃掉帧预算。真正有效的做法几乎都不是优化单次绘制，而是减少绘制次数。

手法省掉了什么量级
锁 30fps一半的帧根本不渲染2×
只画亮格L < 0.06 直接跳过，大面积暗部零成本3–10×
量化 + 缓存样式串把 (色相, 亮度, 白度) 压成几百个 key，rgba() 只拼一次5–20×
小离屏画布降采样交给浏览器，不用自己遍历像素10–100×
字形图集用 drawImage 替代 fillText（列数 200+ 或要 60fps 时才必要）3–10×

注意：列数不是越多越好。列数翻倍，字符数量翻四倍，但细节增益远小于成本， 而且字符会小到认不出来——「字符感」反而丢了。多数好看的实现落在 90–140 列之间。
08 / 该选哪条路

视频只是其中一种素材来源

回到最常被问的那个问题：那些漂亮的 ASCII 效果页面，是「视频 + 滤镜」做的吗？ 答案是很少——它只是「往小画布上画什么」这一层的不同选择而已。

源做法什么时候用
程序化形状用数学直接画进小画布（圆形、贝塞尔、噪声、粒子）最常见。零素材、可控、可交互、分辨率无关
静态图图片 ASCII 化一次，之后只动字符层文本型首屏。重活只干一次，极省
3D 场景渲到 render target，再字符化要立体感、要旋转
真视频 / 摄像头drawImage(video) 每帧采样内容复杂度不受限，代价是体积、自动播放限制、耗电

判断你正在看的页面属于哪种，按这个顺序查：

① Network 里有没有 .mp4 / .webm 请求 → 有就是视频源
② 缩放页面：字符密度随视口连续变化 → 实时采样；纹丝不动只是放大 → 预烘焙
③ 动鼠标：ASCII 跟着变形、避让 → 一定有程序化逻辑
④ 看字符集：标准 " .:-=+*#%@" → 多半是通用库；策展过的混排 → 定制的

这一页本身也是同一套技术的产物：所有演示画面都是程序化生成的， 没有任何图片或视频素材，也没有引入任何库。滚动、拖动滑块时它在实时重算。
