# 「shoal」背景动画 · 复刻分析

> 参考素材：`3WzIRLEUmwL6GDHl.mp4` — 992×990，30fps，452 帧，15.07s（Twitter 抓取，"Twitter-vork muxer"）
> 来源：X @himanshubuildss 展示的 [scrolltide.co](https://scrolltide.co) 案例页，原话：
> *"A page where fish made of letters swim around, and tapping the water feeds them."*

---

## 0. 一句话概括

**这不是"鱼在动"，而是一张固定的方格纸 + 一片字符场 + 若干"鱼形遮罩"在上面缓慢漂移。**
鱼不是由字符拼成的图片，而是**用字符网格去"填充"一个鱼形轮廓**——格子本身不动，动的是轮廓。
想通这一点，整个动画就变成几十行代码；想不通，就会写成"画一堆小方块去追一条路径"，永远做不出这个味道。

---

## 1. 四个决定成败的核心机制

### ① 格纸与字格是同一套网格（最关键）

我用蓝色网格叠在原图上逐格验证：**每一个字符都精确坐在一个 19.5px 的格子里**，一个格子一个字符，居中对齐。

- 纸张网格：**19.5px 均匀**，无主次线
- 字符单元：**正好一个网格 = 19.5px**
- 填充色块：**贴满整格**（full-bleed），正常缩放下看不到间隙或圆角
- 网格相位：竖线 x ≡ 0 (mod 19.5)，横线 y ≡ 17.5 (mod 19.5)

> ⚠️ 测量陷阱：自相关会在 lag=39 处出现最强峰。那是因为 19.5 不是整数，两个周期恰好落在整 39px 上。**别被误导成 39px 主格 + 19.5px 次格**——逐线定位后确认是均匀 19.5。

所以鱼和纸是**同一个坐标系**：鱼不是"贴在纸上"，而是"画在纸上"。

### ② 鱼 = 字符场的遮罩，不是滑动的精灵图

这是我最意外的发现，也是复刻时最容易做错的点。

我做了两组测量：
- 逐帧做单元格色彩指纹匹配 → **1 帧间隔的最佳位移永远是 (0,0)**，误差 2.1–5.2；而 ±1 格的误差高达 21–33。
- 但 **1 秒间隔的最佳位移正好是 (+1, 0) 格**。
- 同时，连续两帧对比能看到个别字符变了（比如某格 `o` → `X`），但**大部分字符原位不动**。

结论：**主体色块以约 1 格/秒 前进，但字符本身并不跟着鱼走**——字符是钉在格子坐标上的，鱼经过时改变的是"这个格子该显示成什么状态"。

正确的心智模型：

```
每格状态 = f(该格与鱼形轮廓的位置关系)
  ├─ 轮廓内部   → 填色块 + 反白字符
  ├─ 轮廓边缘   → 只有深色字符，无底色（溶解感来源）
  └─ 轮廓外部   → 完全空白
```

这就是为什么鱼的边缘是"碎掉"的、为什么字符会像水流穿过鱼身。**用 sprite 平移是做不出这个的。**

### ③ 鱼体可以任意朝向，但字符永远是正的

这点最容易看漏，也是"鱼由字母组成"观感成立的关键。

看参考帧里那条**竖直的鱼**（key_05 顶部，约 7–8 格宽 × 16 格高）：鱼身是竖的，但鱼肚子里每一个字符都是**正的**，没有跟着转。

也就是说：
- **鱼形轮廓（遮罩）可以旋转到任意航向**
- **每个格子里的字符永远正立在纸面上**

如果先把一条"字符鱼"画成图再整体旋转，字符就会歪——一眼假。
正确做法：拿一个鱼形多边形，按航向做旋转变换；对每个格子中心做**点在多边形内**测试，决定该格是"填色/裸字/空"；然后**正着画字符**。

这也解释了为什么参考里的鱼边缘是**阶梯状的**（斜边在方格上必然锯齿化），那种锯齿感恰恰是"画在格纸上"的证据，不要去抗锯齿抹平它。

### ④ 深度靠"不透明度"而不是"景深模糊"


我原本以为中间有一圈白色光晕在做景深。实测否掉了：

**没有径向白光。** 用扣除鱼层的时序中值背景，测纸面亮度随半径变化：

| 距中心半径 | 纸面亮度 |
|---|---|
| 280–320 | 247.1 |
| 360–400 | 247.8 |
| 450–550 | 247.5 |

几乎完全平坦 → 纸面处处 #FAFAF8，**没有白色 vignette**。

**也不是位置相关的景深模糊。** 对 5718 个鱼身格子测边缘锐度，按半径分箱：

| 半径 | 中位锐度 |
|---|---|
| 150–200 | 56.5 |
| 250–300 | 63.8 |
| 400–450 | 63.8 |
| 550–600 | 57.5 |

基本恒定，97% 的格子一样锐利。所以**不要做"越靠中心越糊"**。

真正的手段是：
- **每条鱼按距离分层的整体不透明度**（远处鱼淡到接近纸色）
- **不同尺寸**（远处小、近处大）
- 中心区鱼会**淡出**，保证标题可读
- 搜索框是**毛玻璃面板**——参考帧里能明显看到鱼的模糊色块透进面板底部，这是 `backdrop-filter` 的证据

## 2. 实测规格表

| 项目 | 实测值 |
|---|---|
| 画布 | 992 × 990（近正方，非全屏比例） |
| 纸面 | `#FAFAF8`（暖白，采样 250,250,248） |
| 格线 | `#EEEEEB`，仅比纸面深 **4.8%**，1px |
| 网格间距 | **19.5px** 均匀（≈ 视口宽 2.0%） |
| 字符单元 | 1 格 = 19.5px，一字一格，居中 |
| 鱼体尺寸 | 远景约 **10×7 格**；近景大到 **30×22 格** |
| 字号（标题） | ≈44px @992（= 4.4% 视口宽），字重 ~300 |
| 标题实测包围盒 | 409 × 42 px，水平居中 |
| 搜索框 | ≈622 × 124 px，圆角 ~30，居中 |
| 画面鱼数 | 同时约 5–10 条 |

### 字符集

```
S  X  8  %  #  @  o  t  e  a  s  0  ;  :  ,  .  '
```

规律：**重笔画字符（# % 8 S X）集中在鱼身核心**，标点/小写（; : , . ' t o）在溶解边缘。
- 填色格 → 字符反白（近白）
- 裸字符格 → 深暖灰 `#6F6152`

### 配色（实测色族质心）

| 色族 | 质心 |
|---|---|
| 砖红 / terracotta | `#A7695D` |
| 灰粉 / dusty salmon | `#B8947C` |
| 橄榄 / ochre | `#BEB182` |
| 石板蓝 / slate | `#868B9C` |
| 中性暖灰 / taupe | ≈ `#B09D91` |

**关键细节（这里我一开始判断错了，已修正）**：我采样了 141 个填色格，**没有任何两个格子颜色相同**。
最初的结论是"每格做 ±10% 随机明度抖动"。**实测否掉了**：

| 测量（仅统计鱼体内室格，排除边界混入纸色） | 结果 |
|---|---|
| 相邻格平均色差 | **22.8** |
| 同一条鱼内随机两格色差 | 44.4 |
| 若每格独立抖动，相邻格应为（1.128σ） | **44.1** |

相邻色差只有独立预测值的 **51%** → 这是一片**平滑的二维色调场**，不是逐格随机噪声。
另有弱的方向性：沿鱼身长轴有 r ≈ **−0.26** 的明暗渐变，沿背腹轴几乎没有（r=+0.02）。

> 所以鱼身的"肉感"来自**平滑的明暗渐变**（像被光照过的物体），不是噪点。
> 复刻时如果写成逐格 `random()` 抖动，鱼会变成"一张均匀色的贴纸贴上去"，永远平面。这是我第一版复刻偏平的直接原因。

### 字体

- **标题/正文**：几何无衬线，Light(~300)，**单层 g**、双层 a、圆形 o/c，字距正常偏紧。
  最接近的免费替代：**Jost / Questrial / Outfit**；商用原版大概率是 **PP Neue Montreal / Söhne / Aeonik** 一类。
- **小字**（`history 03`、`shallow` / `deep`、`cast ⌾ netline ⌗ tap the water to feed them`）：**等宽字体**，~13–14px，字距略宽。替代：**JetBrains Mono / IBM Plex Mono / Geist Mono**。
- 文字色：标题 `#1B1B18`，placeholder `#ABABA9`。

### UI 清单

- 左上：`shoal` 字标 + **5 个方块组成的小标记**（3 红 + 1 浅灰 / 2 黑，错位排列）——本身就是"一群鱼"的像素化，同样落在 19.5px 网格上
- 右上：`history 03`（等宽，`03` 更浅）+ 月亮图标圆形按钮（1px 边）
- 中心：标题 `what's surfacing today?`
- 搜索卡：圆角矩形、毛玻璃、大柔光投影、1px 浅边；`Ask Shoal anything…`；左侧 `+` 圆钮；`shallow | deep` 分段控件（选中项为白底胶囊）；右侧深色圆形提交钮 `↗`（空态为浅灰禁用感）
- 卡下：`cast ⌾ netline ⌗ tap the water to feed them`（等宽小字）

## 3. 运动模型（实测）

| 量 | 实测 | 换算 |
|---|---|---|
| 鱼身位移 | **1 格 / 秒** | **≈20 px/s** ≈ 视口宽 2%/s |
| 横穿 992px 画面 | ≈ 50 秒 | 极慢、极其从容 |
| 方向 | 以水平为主（di 显著，dj ≈ 0） | 缓慢横向巡游 |
| 字符变化 | 局部、偶发（个别格换字） | 不是每帧全部重掷 |

> 另有一个坑：逐帧差分在 **第 90 / 180 / 270 / 360 / 450 帧**（正好每 3.0s）出现尖峰。
> 我验证过 `|f0 − f90| = 11.0`、且 f0 在全片找不到任何相似帧 → **不是 3 秒循环**，是编码器的 GOP 关键帧（90 帧）伪影。别把它当成动画周期。

参考的观感目标：**慢到你几乎注意不到它在动**，只在余光里"余光有感"。一旦做快了，气质就全毁了。

## 4. 交互（喂食）

推文描述是"点水面就能喂鱼"。但这个 15s 片段里**没有出现光标、也没有涟漪**——它是纯待机态（idle）录制。所以喂食动画的细节我无法从素材实测。

可以确定的部分：`tap the water to feed them` 是页面自己的提示文案，说明点击水面是核心交互；从设计逻辑推断，合理实现是：

1. 点击点生成 2–3 圈扩散涟漪（细线，向外扩散并淡出）
2. 半径内最近的鱼**转向**点击点并加速靠拢
3. 到达后短暂停留，然后恢复原巡游

复刻时这部分属于"合理再创作"，不必强求与原件一致。

## 5. 复刻实现配方

```
层 0  纸面 #FAFAF8
层 1  格纸 19.5px，#EEEEEB，1px（离屏画布画一次）
层 2  字符场 / 鱼群（canvas，按格计算状态）
层 3  —— 无白色 vignette ——
层 4  搜索卡（backdrop-filter: blur(20px+)）→ 鱼的模糊色块会透进来
层 5  标题 / 角标 / 页脚
层 6  涟漪 + 喂食粒子
```

关键实现要点：

1. **把鱼位置吸附到整格**：`cellX = round(t * 20 / 19.5)`。参考里就是整格跳变的（实测相邻帧位移 0 格、1 秒位移 1 格），不吸附会显得"飘"。
2. **字符按格子坐标存**，不按鱼的局部坐标存。这是做出"水流穿过鱼身"观感的关键。
3. **每格明度随机抖动 ±10%**，且**一次生成、不要每帧重掷**（否则会闪）。
4. **性能**：别每帧画几千个 rect。按"鱼 sprite"预渲染到离屏 canvas 再整体变换，或者只重绘脏格。
5. **必做**：`prefers-reduced-motion` 降级、`devicePixelRatio` 适配、页面隐藏时暂停 rAF。

## 6. 三个最容易做错的地方

| 坑 | 后果 | 正确做法 |
|---|---|---|
| 把网格当成 39px（自相关误导） | 字格和纸不重合，整体发糊 | 用 19.5px，逐线定位确认相位 |
| 用滑动 sprite 装字符 | 字符跟着鱼走，假的、死板 | 字符钉在格子坐标上，鱼只改格子状态 |
| 加中心白色光晕 / 径向模糊 | 纸面被洗白、失去"纸"的质感 | 不加。用鱼的 alpha 淡出 + 毛玻璃卡保可读性 |

## 7. 原版是不是"视频转 ASCII"？

先说结论：**很可能是"把一段动画逐帧栅格化成字符网格"，但不是朴素的"亮度→字符"映射，也不是手摆的 ASCII 精灵图。**

说明：我尝试去核实原站，但推文链接指向的是展示站 scrolltide.co，实际页面没拿到，所以**以下全部是从视频本身反推的，不是读源码**。

### 支持"逐帧栅格化一张图/视频"的证据

| 证据 | 实测 | 为什么指向栅格化 |
|---|---|---|
| **朝向连续分布** | 36 条可测鱼的主轴角度铺满 0–180°，仅 39% 落在水平/垂直 12° 内，25% 明显是斜的 | 若是几张手绘轴对齐精灵图，角度会聚在 0/90 |
| **鱼身内部是平滑色调场** | 相邻格色差仅为独立预测的 51% | 说明颜色采样自一张连续图像，而非程序逐格抖动 |
| **三态结构** | 内室=色块+反白字 / 边缘=裸深字 / 外部=空白纸 | 这正是**带 alpha 通道**的图像被阈值切成三段的典型结果 |
| **字符永远正立** | 鱼可任意旋转，字符始终正立在格纸坐标系里 | 栅格化的必然产物：网格是固定的，内容在动 |
| **色彩全部唯一** | 141 个填色格，无两格同色 | 采样自连续图像才会这样 |

### 反证 / 不支持的地方

| 证据 | 实测 | 冲突点 |
|---|---|---|
| **没有反荫蔽（countershading）** | 沿背腹轴明度相关 r = **−0.02**，仅 7% 的鱼 \|r\|>0.5 | 真实鱼片一定"背深腹浅"。没有 → 更像风格化 3D / 程序化动画，而不是实拍素材 |
| **运动太慢** | 约 1 格/秒 = 20px/s | 实拍鱼要放慢 ~10 倍才这样 |
| **两种字符渲染风格** | 色块上是反白字，裸格是深字 | 朴素"亮度→字符"斜坡不会产生两套风格；必须额外知道"在鱼里/在鱼外" |
| **字符不是每帧乱翻** | 相邻帧只有个别格换字，NCC 稳定在 ~0.9 | 30fps 逐帧重算字符通常会更"跳" |

### 我的判断

最贴合全部证据的管线是：

```
一段带 alpha 的鱼动画（大概率是风格化 3D / 程序化渲染）
    ↓ 每帧降采样到 19.5px 网格
    ↓ 逐格：alpha 高 → 色块 + 反白字符
            alpha 中 → 裸深色字符
            alpha 低 → 空
    ↓ 字符从固定字符集里按色调/密度挑（重笔画在核心，标点在边缘）
    ↓ 字符永远画正，不跟随旋转
```

也就是说：**"视频转 ASCII"这个方向是对的，但它转的不是实拍鱼片，而更像一段生成的鱼动画；而且不是简单的亮度映射，是 alpha + 色调两路一起决定的。**

### 如果你想自己验证

打开原站，看这三件事就能定论：
1. DevTools 里有 `<video>` 元素或 `.webm/.mp4` 请求 → 实锤视频转 ASCII
2. Canvas 每帧的 `getImageData` 只读一张离屏图 → 栅格化
3. 缩放浏览器：网格间距跟着视口宽度按比例变（我实测 19.5/992 ≈ 2.0%），若字符数量随分辨率连续变化，说明是逐格采样而非固定 sprite
